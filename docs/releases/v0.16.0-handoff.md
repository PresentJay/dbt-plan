# 0.16.0 릴리즈 핸드오프

이 PR은 릴리즈 준비다. 기준은 `v0.15.0` 이후 `main`에 반영된 변경이며,
PR #200의 최종 수정과 PR #209의 기여 안내를 포함한다.
브랜치는 `release-0.16.0`, 대상은 `main`이다. PR 밖의 미병합 기능은 포함하지 않는다.

## 준비 내용

- `pyproject.toml`, `src/dbt_plan/__init__.py`, `server.json`의 서버·패키지 버전,
  `uv.lock`의 프로젝트 버전을 모두 `0.16.0`으로 맞췄다.
- `CHANGELOG.md`에 0.16.0 변경을 묶고 [공개 릴리즈 노트](v0.16.0.md)를 준비했다.
- [마이그레이션 문서](../exit-codes.md)에 적용 버전을 명시했다.
- 동작 구현은 이미 main에 병합돼 있다. 이 PR은 버전과 문서만 변경한다.

확인해야 할 호환성 변경은 실행 오류의 종료 코드 `3`, `warning_exit_code: 3`
금지, 잘못된 `--select` 거부다. 새로 생성한 CI는 완료된 경고를 기본 허용하고
실행 오류는 항상 차단하므로, 소비자에게 워크플로 재생성과 정책 검토를 안내한다.

## 검증 기준

릴리즈 PR의 최신 커밋에서 필수 CI 14개가 모두 통과해야 한다. 로컬에서는
wheel/sdist를 빌드한 뒤 `tests/test_packaging.py`를 건너뜀 없이 실행하고,
버전·MCP 메타데이터·릴리즈 워크플로·문서를 확인한다. PR 본문에 실제 검증
결과와 CI 링크를 남긴다. 이후 커밋이 추가되면 그 커밋의 검사를 다시 확인한다.

## 발행 순서

아래 명령은 배포 담당자가 실행할 절차다. PR 생성만으로 실행되지 않는다.

1. 릴리즈 날짜를 확인한다. 현재 CHANGELOG의 날짜는 `2026-09-09`이며,
   실제 발행일이 달라지면 PR에서 수정하고 새 CI 결과를 확인한다.
2. 최신 CI를 확인하고 릴리즈 PR을 머지한다. 저장소는 자동 머지를 지원하지
   않으므로 진행 중인 검사는 끝날 때까지 기다린다.

   ```bash
   gh pr checks release-0.16.0 --required
   release_head=$(gh pr view release-0.16.0 --json headRefOid --jq .headRefOid)
   gh pr merge release-0.16.0 --squash --match-head-commit "$release_head"
   ```

3. 머지 커밋을 확인하고 **그 커밋**에 태그를 단다. 움직이는 main의 HEAD를
   그대로 태그하면 사이에 병합된 다른 변경을 포함할 수 있다.

   ```bash
   release_commit=$(gh pr view release-0.16.0 --json mergeCommit --jq .mergeCommit.oid)
   git fetch origin main --tags
   git show "$release_commit:pyproject.toml"
   git tag -a v0.16.0 "$release_commit" -m "dbt-plan v0.16.0"
   git push origin refs/tags/v0.16.0
   ```

   기존 `v0.16.0` 태그가 있으면 덮어쓰지 말고 발행 상태부터 확인한다.

4. 태그 푸시는 `.github/workflows/release.yml`을 시작한다. 실행 순서는
   버전 확인 → 테스트 → 빌드 → 패키징 검사 → PyPI → GitHub Release → MCP
   레지스트리다. PR 머지와 태그 푸시는 서로 다른 단계다.

   ```bash
   gh run list --workflow release.yml --limit 5
   ```

   출력에서 `v0.16.0` 태그의 실행 ID를 골라 `gh run watch <실행-ID> --exit-status`로
   확인한다. `release`와 `publish-registry` 두 작업이 모두 성공해야 한다.

5. 자동 생성된 GitHub Release 설명을 준비한 노트로 교체한다. 사용 중인
   checkout이 달라도 정확한 태그의 노트를 읽도록 한다.

   ```bash
   git show v0.16.0:docs/releases/v0.16.0.md > /tmp/dbt-plan-v0.16.0-notes.md
   gh release edit v0.16.0 \
     --title "v0.16.0 — stronger safety checks and explicit CI errors" \
     --notes-file /tmp/dbt-plan-v0.16.0-notes.md
   ```

6. PyPI에서 `dbt-plan==0.16.0`을 새 가상환경에 설치해
   `dbt-plan --version`을 확인한다. GitHub Release의 wheel/sdist 첨부와
   MCP 레지스트리의 서버·패키지 버전도 `0.16.0`인지 확인한다.

## 실패 시 처리

- PyPI 발행 전에 실패하면 오류를 수정하고 재시도한다. 릴리즈 전용 태그를
  다시 쓰기 전에 PyPI와 GitHub에 실제로 발행됐는지 확인한다.
- PyPI 발행 뒤 GitHub Release 생성이나 MCP 등록만 실패할 수 있다.
  이 경우 패키지는 이미 공개된 상태다. 전체 발행을 무작정 다시 실행하지 말고
  실패한 단계만 복구한다. 같은 버전의 패키지를 교체하려고 하지 않는다.
- `publish-registry`만 실패하면 성공한 PyPI 발행은 유지된다. 워크플로에서
  실패한 작업을 재실행하거나, 해당 태그의 `server.json`으로 인증된
  `mcp-publisher publish`를 실행해 등록을 복구한다.
- Marketplace용 `v1` 태그 갱신은 별도 결정이다. 이번 패키지 릴리즈 절차에서
  이동하지 않으며, `v1` 자체는 PyPI 발행 워크플로를 시작하지 않는다.

발행 후에는 설치 버전, Release URL, 두 작업의 성공 상태를 후속 기록으로 남긴다.
